## Fixed (P2 — layout-property animations)

- ~~`AnalyticsDashboard.vue:1190` — `transition: width`~~ — the 5 horizontal-bar fills (`.ad-hbar-fill`, used by `ebaBars`, `ebaFilterBreakdown`, `topicBreakdown`, `pageBars`, `browserBars`) now render at a fixed `width: 100%` and animate `transform: scaleX(pct/100)` with `transform-origin: left` instead of animating `width` directly.

- ~~`style.css:1199` — `transition: max-width, padding, margin`~~ — this one is a genuine exception, not a like-for-like swap: it animates VitePress's own `.VPDoc`/`.content`/`.content-container` on reading-mode toggle, which reflows body text (line-break recalculation), something `transform`/`opacity` can't reproduce without visibly distorting text. Added `contain: layout` to the three selectors so the reflow this transition triggers stays scoped to that subtree instead of forcing a full-page layout pass — same idea as the audit's fix, applied via containment since the animated properties themselves can't be swapped out here.

## Fixed (P2 — OS-level `prefers-reduced-motion` respected)

- ~~No OS-level `prefers-reduced-motion` query~~ — `AccessibilityControls.vue`'s `onMounted` now checks `localStorage.getItem(LS_MOTION)` first (an explicit in-app choice, either on or off, always wins) and only when nothing is stored falls back to `window.matchMedia('(prefers-reduced-motion: reduce)').matches` to seed `toggleState.reducedMotion`/`applyReducedMotion`. A pure CSS `@media (prefers-reduced-motion: reduce)` mirror was considered and rejected: it would have forced reduced motion even for a user who explicitly toggled it *off* in-app despite an OS-level preference, overriding their explicit choice — the JS init preserves that precedence.

Verified via `npm run docs:build` (exit 0, no SSR errors, build completed in 134.99s).
